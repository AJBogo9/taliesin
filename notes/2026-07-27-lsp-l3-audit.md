## L3-1 — one malformed message and the server is gone · **the real one**

`main_loop` wraps dispatch in `serve::guarded`, whose comment states the property exactly: a
failure must leave "one failed call rather than a dead server", because otherwise "every later
request from the editor goes unanswered, silently".

`guarded` catches **panics**. The seven `serde_json::from_value(req.params)?` sites in the dispatch
do not panic — they return `Err`, which `Ok(sent) => sent?` propagated straight out of `main_loop`
→ `run` → `cmd_lsp`, which logged it and returned `ExitCode::FAILURE`. So the guard's stated goal
was defeated by the *more likely* path (serde rejects malformed input as a matter of course;
panics are the residual case the guard was written for), and with a worse outcome than the one it
prevents: not a quiet server, an **exited process**.

**Measured**, release binary, one message per fresh session, "kills" = a known-good request
answered before and not after:

| client message shape | before | after |
|---|---|---|
| `completion` with `context: {}` (no `triggerKind`) | **exit 1** | survives |
| `hover` with a float position (`line: 4.0`) | **exit 1** | survives |
| `hover` with a negative position (`line: -1`) | **exit 1** | survives |
| `rename` with `newName: null` | **exit 1** | survives |
| `didOpen` with an `untitled:` URI (VS Code's unsaved buffer) | survives | survives |
| `codeAction` with a string `data` on the diagnostic | survives | survives |
| `hover` far past EOF (`line: 999999`) | survives | survives |
| `didChange` carrying an incremental (range) change | survives | survives |

**4 of 8 → 0 of 8.**

**Who this lands on.** The VS Code companion has its own TypeScript providers
(`editor/vscode/src/{complete,hover,definition-provider,outline-provider}.ts`) and never spawns
`taliesin lsp` — grep for `lsp` in `extension.ts` + `package.json` returns nothing. So *every*
client of this server is a third-party editor whose exact message shapes this repo does not
control, which is the population the table above is about. The one shape that mattered most was
not a hostile input: it was a client that sends a field the spec makes optional and `lsp_types`
makes required.

**Fix.** Both dispatch arms now treat `Ok(Err(_))` as a first-class outcome: a request is answered
with **InvalidParams** (`-32602`) and the session lives; a notification is logged and skipped.
InvalidParams is accurate for every reachable error — `handle_request`'s other two error sites are
serializing our own `lsp_types` response (cannot fail) and the channel send (only fails once the
client is gone, and then the error reply fails too and `?` correctly ends the session).

Pinned by `lsp::tests::a_malformed_message_does_not_kill_the_session`, deliberately written as the
sibling of the existing `a_panicking_message_does_not_kill_the_session` — the two halves of one
property, which is why the gap was invisible: the panic half was tested, so the property *looked*
covered.

## L3-2 — the front-matter closer offers front-matter keys

Typing `---` to close the front matter popped the entire **27-key** list. The delimiter is all
`-`, which `is_id_char` admits, so `is_frontmatter_key_line` read it as a partial key.
`in_frontmatter` cannot catch it: it deliberately ignores the current line so a cursor *on* a key
line still counts as inside the block. A key never opens with `-` or `.`, so excluding those also
covers the rarer `...` terminator and a YAML `- ` list dash. Measured: 27 items → 0.

## L3-3 — only the first class of a fenced div completes

`is_div_class_context` required `{` immediately before the `.`, so in `::: {.theorem .` the second
`.` saw a space and gave up. `divs.rs` collects classes into a `Vec` and `join(" ")`s them, so a
multi-class div is rendered syntax, not a typo — completion was the only half that stopped at one.
Measured at the second `.`: 0 items → 22.

**The corpus does not exercise this**, which is why it survived: every multi-attribute opener in
the tree is `.class` followed by `#id` or `key=` (`::: {.theorem #thm-lagrange title="Lagrange"}`),
never a second `.class`. Checked before fixing — the renderer's support is what makes it a defect
rather than a matching limitation.

## L3-4 — a worktree in one session reddens the guard in every other

Found by accident: the full suite went red at `retired_names` on a branch that touches neither
`notes/` nor any retired name. All 86 occurrences were in
`.claude/worktrees/deck-letterbox/notes/*.md` — a parallel session's worktree, which is a **full
second checkout** and therefore carries its own `notes/`.

`SKIP_PATHS` already lists `notes`, but it is matched as a prefix **from the repo root**, so it
covers `notes/` and not `.claude/worktrees/<branch>/notes/`. The directory is gitignored (via
`.git/info/exclude`), so it is invisible to `git status` and fully visible to the test's own
filesystem walk. Worktrees are a standing practice here, so this recurs every time two sessions
overlap, and it presents as *your* branch breaking a guard about a rename you never touched.

## Measured healthy — the every-keystroke path

Worth stating because the code reads alarming: `didOpen`/`didChange` run `render_single_doc` **and**
`anchors_defined_elsewhere_in_project` — which walks the project and re-reads, include-resolves and
anchor-scans every *other* page — synchronously, in a single-threaded loop, with no debounce and no
cache. Hover and completion each render the buffer again.

It is fine at repo scale. Median over 5 edits, release binary:

| document | project | keystroke | hover | completion | outline |
|---|---|---|---|---|---|
| `docs/guide/reference/cli.tmd` (486 lines) | 22 pages, `_site.yml` | **5.3 ms** | 3.3 ms | 3.1 ms | 0.7 ms |
| `corpus/posts/born-machines.tmd` (494 lines) | none | **1.9 ms** | 0.2 ms | 0.2 ms | 0.7 ms |

The delta between the rows is the project-wide scan (22 pages ≈ 3.4 ms). The largest project in the
tree is that same 22-page guide, so nothing here is close to a perceptible edit. **Not filed as a
finding** — the scaling is linear in page count and no document in the corpus reaches a size where
it matters. Worth re-measuring only if a book an order of magnitude larger ever exists.

## The MCP loop is immune, and the contrast is the lesson

`mcp.rs` has the same shape — a persistent stdio JSON-RPC loop, the same `serve::guarded` panic
boundary, the same comment about not killing the session — and **cannot** fail this way. Checked,
not assumed:

- `handle` returns `Result<Value, (i64, String)>`: an error is a **value** carrying its own
  JSON-RPC code, so the loop turns it into a response and continues (`mcp.rs:106-113`).
- It hand-reads `req.get("params")` off a `serde_json::Value` instead of deserializing into typed
  structs, so there is no `?` on a parse to escape in the first place.
- A malformed *line* is answered `-32700 parse error` and the loop `continue`s (`mcp.rs:96-101`).

Same author, same week, two stdio JSON-RPC servers. The difference is not care, it is that the LSP
uses typed `lsp_types` params and therefore has a `?` on every dispatch arm, and `?` in a loop body
is a **process exit** when the loop is the program. *A panic boundary around a dispatch that also
returns `Err` guards half the door.* Worth checking the next time a long-lived loop grows a typed
deserialization step.
