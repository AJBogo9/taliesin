# Audit Wave 1 Execution Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the four launch-critical audit rounds (R1 adoption friction, R3 pre-mortem, R4 technical due diligence, R5 document-as-attack-vector) and bank their findings as numbered backlog items, without disturbing a concurrent session on the same tree.

**Architecture:** Four independent read-mostly rounds dispatched as parallel subagents, each writing exactly one dated findings file under `notes/`. No round edits shared state. A fifth coordinating task, run by the main session only, merges accepted findings into `notes/backlog.md` and the round index in `notes/AUDITS.md`.

**Tech Stack:** No code is written in this wave. Tools are: repository reading (Read/Grep/Glob), `git log` (read-only), web research, and for Task 4 only, one clean-clone build.

**Spec:** [2026-07-27-audit-slate-design.md](../specs/2026-07-27-audit-slate-design.md). Each task below restates its round's brief in full, so a worker never needs to open the spec.

## Global Constraints

Every task's requirements implicitly include all of this.

- **A filed cause is a hypothesis.** Every finding states the measurement that produced it and what observation would refute it. An inference is not a finding.
- **Trust the symptom, never the stated cause, line number or cost.** Re-derive from source.
- **A finding that names one instance has not enumerated the shape.** Enumerate before filing.
- **Hard scope guard.** HTML is the only output target. No CDN or network egress. The preview never writes back to source. Prefer a better default over a new configuration knob. A finding requiring one of these violations is a scope error, not a finding.
- **Settled rulings may be costed, never reversed:** the `AGPL-3.0-only` licence, HTML-only output, and the `MAX_WARM_PAGES` plus LRU eviction freeze in `serve_site/exec_pool.rs`.
- **Check `notes/backlog.md`'s "Do not re-add / re-scope" list before filing anything.**
- **A confirmation is a valid result.** "Measured, healthy" gets recorded.
- **Never run `pkill -f taliesin`.** It kills the concurrent session's servers and the running shell. Kill by PID only.
- **No task edits `notes/backlog.md`, `notes/AUDITS.md` or `notes/LESSONS.md`.** Only Task 5 touches those.
- **Read-only git for subagents.** No commits, no branch switching, no `git checkout`, no `git restore`.
- **Bound compilation:** any task that compiles sets `CARGO_BUILD_JOBS=4`. Heavy cargo runs are charged to the VS Code cgroup and have previously killed the desktop.
- **Reserved item-number blocks**, so two rounds cannot collide: R1 = **79-88**, R3 = **89-98**, R4 = **99-108**, R5 = **109-118**. Numbers are stable and never reused.

- [ ] **Step 1: Dispatch the round**

Dispatch one subagent, worktree-isolated, with this brief verbatim:

> You are running an audit round on Taliesin, a Rust dev server that renders `.tmd` files to HTML only. Repository root is the working directory. Read `CLAUDE.md` first for project context.
>
> **Your question:** What stops someone from switching to Taliesin, given that they already like it?
>
> **Why this round exists.** Taliesin has run four "demand probe" rounds (see `notes/2026-07-22-corpus-demand-probe-*.md` and `notes/2026-07-26-corpus-demand-probe-analyst.md`). All four measured *pull*: can a persona finish a task. The Jobs-to-be-Done literature's central result is that the switching equation is `Push + Pull > Anxiety + Habit`, and that teams over-invest in pull while anxiety and habit are what actually block adoption. This project has measured one term of four. You are measuring the other three, with emphasis on anxiety.
>
> **Method.** Build the four-forces model for three switcher profiles: (a) a Quarto user, (b) a Jupyter or marimo user, (c) a plain-Markdown or mdBook user. For each profile enumerate push, pull, anxiety and habit from evidence rather than imagination: real forum and issue-tracker language where you can find it via web search, and the repository's own artefacts where you cannot. Then rank the anxiety-reducers by cost against blocking power.
>
> **Targets.** `README.md`, the opening pages of `docs/guide/` and `docs/internals/`, the marketing site copy under `corpus/tech-blog/`, the `taliesin init` scaffold output, `LICENSE`, and the absence of any exit path.
>
> **Threads to test, not to assume.** These are hypotheses drawn from a scoping pass; confirm or refute each: the `AGPL-3.0-only` licence; bus factor of 1 with no `CONTRIBUTING.md`; no PDF or other export escape hatch (a deliberate invariant that nonetheless reads as lock-in to an evaluator); `.tmd` as a novel file extension; no visible answer to "who else uses this"; no documented import path from an existing corpus.
>
> **Deliverable.** Write `notes/2026-07-27-adoption-friction-audit.md` containing: the four-forces table per profile; a ranked anxiety register where each entry names the specific artefact that would reduce it (a paragraph, a command, a page); and an explicit list of anxieties the project should *accept* rather than fix, with reasoning. End with a "Proposed items" section numbering findings from **79** upward, at most ten.
>
> **Traps.** Do not convert this into a feature wishlist; the output is mostly words and affordances, not code. Do not propose changing the licence or adding an output format: both are settled owner rulings, and your job is to name their cost, not reverse them. Check the "Do not re-add / re-scope" list at the bottom of `notes/backlog.md` before filing anything.
>
> **Constraints.** Read-only git. Do not edit `notes/backlog.md`, `notes/AUDITS.md` or `notes/LESSONS.md`. Never run `pkill`. Write exactly one file.

## Task 2: R3, pre-mortem

**Files:**
- Create: `notes/2026-07-27-premortem-audit.md`
- Read: `notes/backlog.md`, `notes/ROADMAP.md`, `README.md`, `CLAUDE.md`
- Item numbers: **89-98**

**Interfaces:**
- Consumes: nothing. Fully independent, and deliberately so — it must not be anchored by the other rounds' findings.
- Produces: a clustered failure register. Task 5 reads its "Proposed items" section.

- [ ] **Step 1: Dispatch the round**

Dispatch one subagent with this brief verbatim:

> You are running a pre-mortem on Taliesin, a Rust dev server that renders `.tmd` files to HTML only, authored by one person over 1,581 commits and about to be published publicly. Read `CLAUDE.md` and `notes/backlog.md` for context.
>
> **Your premise, asserted as fact and not as possibility:** It is mid-2027. Taliesin was published and it failed. Your job is to explain why.
>
> **Why this round exists.** Every audit this project has run asks what is wrong *now*. This asks what will kill the project *later*, which is a different cognitive stance and reliably surfaces different material. Prospective hindsight improves risk-identification accuracy by roughly 30% over asking "what could go wrong."
>
> **Method, and the order matters.**
> 1. Assert the failure as fact. No hedging, no "might."
> 2. **Independent silent generation first.** Write every reason for the failure you can produce, before any evaluation, filtering or clustering. This is the step that carries the value. Do not filter against the owner's known rulings during this step. Aim for volume and include reasons that feel impolitic.
> 3. Only then consolidate the list.
> 4. Only then cluster, rank by plausibility against impact, and identify mitigations.
>
> Run at least three distinct failure framings so the output is not one story: (a) nobody adopted it; (b) people adopted it and then left; (c) it succeeded and became unmaintainable.
>
> **Deliverable.** Write `notes/2026-07-27-premortem-audit.md` containing: the raw unfiltered reason list from step 2 (keep it, do not tidy it away, it is evidence); the clustered failure register with plausibility and impact; and mitigations. End with two sections: "Cheap to insure against now, expensive later" and a "Proposed items" section numbering findings from **89** upward, at most ten.
>
> **Traps.** The documented failure mode of this technique is running it with an authority present, which collapses candour. Applied here: do not pre-filter reasons against the owner's rulings during step 2. Filter in step 4, never in step 2. Do not propose reversing settled rulings (the `AGPL-3.0-only` licence, HTML-only output, the `exec_pool.rs` eviction freeze); you may name their cost.
>
> **Constraints.** Read-only git. Do not edit `notes/backlog.md`, `notes/AUDITS.md` or `notes/LESSONS.md`. Never run `pkill`. Write exactly one file.

- [ ] **Step 2: Verify the output against the shared contract**

Read the produced file and confirm. Reject and re-dispatch if any fails:

```
1. The raw unfiltered list from step 2 is present in the document.
   If it was tidied away, the method was not followed.
2. All three failure framings are covered.
3. Proposed items are numbered 89-98 and no higher.
4. No finding proposes reversing a settled ruling; costing them is allowed.
5. At least one reason in the raw list is genuinely uncomfortable.
   A pre-mortem with no impolitic entries did not do step 2.
```

- [ ] **Step 3: Record the verification result**

Append a reviewer note stating which checks passed and any rejected finding.

## Task 4: R5, the document as attack vector

**Files:**
- Create: `notes/2026-07-27-untrusted-document-audit.md`
- Read: `crates/core/src/includes.rs`, `crates/server/src/exec.rs`, `crates/server/src/kernel.rs`, `crates/core/src/render/extension/`, `crates/server/src/headless_js.rs`, `SECURITY.md`
- Item numbers: **109-118**

**Interfaces:**
- Consumes: nothing from other tasks.
- Produces: a threat model with a controls table. Task 5 reads its "Proposed items" section.

- [ ] **Step 1: Dispatch the round**

Dispatch one subagent with this brief verbatim:

> You are running a threat-modelling round on Taliesin, a Rust dev server that renders `.tmd` files to HTML only. Read `CLAUDE.md` first.
>
> **Your question:** What happens when a user opens a `.tmd` document they did not write?
>
> **Why this round exists.** `.tmd` executes code by design: `{python}`, `{r}` and `{js}` cells all run. Before publication every document was the author's own, so this threat model did not exist. Publication creates it, because documents get shared. The 2026-07-17 security round audited Taliesin as a *program*; you are auditing `.tmd` as a *format that arrives from elsewhere*.
>
> **Method.** Threat-model the untrusted document. Walk every path a hostile or merely careless `.tmd` can reach, and for each establish (a) what it can do, (b) whether an existing control stops it, and (c) what the user is told. Paths to cover at minimum:
> - code cells executing against the warm Jupyter kernel (`exec.rs`, `kernel.rs`)
> - `{{< include >}}` path traversal and the containment root (`includes.rs`)
> - shortcode arguments and the extension expansion path (`render/extension/`)
> - front-matter values reaching the page
> - `{js}` cells running in the reader's browser
> - `mounts:` serving another project
> - asset paths and what gets copied into a build
> - the headless browser path (`headless_js.rs`)
> - the preview server's exposure under `--host`
>
> **Deliverable.** Write `notes/2026-07-27-untrusted-document-audit.md` containing: a controls table (path, capability, existing control, what the user is told); the gaps; and a clear recommendation on what to **document** versus what to **enforce**. State an explicit position on the central question: is executing an untrusted `.tmd` *meant* to be safe, or is it meant to be understood as running someone else's code, in which case the correct deliverable is a discoverable warning rather than a sandbox. End with a "Proposed items" section numbering findings from **109** upward, at most ten.
>
> **Traps.** **Do not design a sandbox.** Executing code is the product, not an accident, and the likely correct answer is documentation plus a consent affordance rather than containment. Read `SECURITY.md` first: it may already take a position, in which case the finding is whether that position is *discoverable* by someone about to open a stranger's document. Note that `includes.rs` containment and symlink handling are already test-pinned (`crates/core/tests/symlink_containment.rs`, `include_root_parity.rs`), so read those tests before claiming a traversal gap; a previously filed symlink-loop SIGABRT was refuted and must not be re-filed.
>
> **Constraints.** Read-only git. Do not edit `notes/backlog.md`, `notes/AUDITS.md` or `notes/LESSONS.md`. Never run `pkill`. Do not execute any hostile document against a live kernel on this machine; reason from source and from the existing tests. Write exactly one file.
